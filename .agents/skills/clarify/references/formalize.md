# 正式化：从 Work 收成 Quick / Full（按需读）

> 何时读：用户要收束 / 定下来 / 存档 / 计入验证；要保存或复盘 ThinkingCase；重大难逆事项准备确认不可逆承诺。读完按 Step 0–5 执行；到期复盘见 `review.md`。

以下情况才**提议或接受**从 Work 转入正式化：

1. 用户明确要「收束 / 定下来 / 形成正式决策 / 把下一步作为承诺 / 存档 / 计入验证」；
2. 用户要把对话保存为 ThinkingCase 或复盘既有 Case；
3. 重大、高代价、难逆或影响多人的事项准备确认不可逆行动或冻结承诺时，Copilot 在给出必要的可逆安全缓冲后提议 Full，用户明确接受。

转换时可以只问一句「要不要现在收成 Quick / Full？」用户也可以拒绝并继续 Work。高风险情境若拒绝正式化，仍可继续探索、比较和采用可逆的临时保护动作，但不得认可不可逆承诺，也不得把探索性分析伪装成已经完成的重大决策。进入 Quick / Full 时先综合已有对话，只补真正缺失的信息，**不从头重跑问卷、不要求用户复述已经说过的内容**。

只有两档、两种视角：

| | 自诊 | 他诊 |
|---|---|---|
| **Quick** | 自己的日常卡点 | 帮别人快速理清 |
| **Full** | 自己的重大判断 / 消化外部建议 | 帮别人处理重大、高代价或不可逆判断 |

**Work 不在这张表里，因为它不是处理深度。视角也不是第三档。** Quick 都用 `templates/case-quick.md`，Full 都用 `templates/case-full.md`；模板内记录视角。不存在固定的「他诊流程」或 `case-work.md`。

正式化时的两条铁律：

1. **框架组织观察，不生产答案。** 判断由可区分的证据与 `Case Owner` 的裁决支持；个人经验、外部建议和案例只能作为有边界的证据，不能自动变成结论。
2. **先综合，再收束。** Work 可以提供有边界的临时判断；正式结论、行动承诺或 Case 记录之前，才完成最小 Clarity Triage 与路由。

流程：

```text
GPT Work（默认，可自然结束）
  → 用户要正式收束 / 落盘 / 验证，或重大事项要确认不可逆承诺
  → 从已有对话综合最小 Clarity Triage
  → no_framework / evidence_first / cannot_proceed / Quick / Full
  → （Quick / Full 才需要时）按 CATALOG 当前路由选 0–2 个框架
  → 追问与 Owner 裁决
  → 出口合同
  → 按记录规则决定是否写 cases/THK-NNN
```

---

## Step 0 · 正式化前的最小 Clarity Triage

仅在准备正式收束时执行。先从已有对话综合以下三件事；已经明确的不要重问，信息拿不到就记为 `unknown`，不能靠猜：

1. **Case Owner**：谁拥有目标、作最终决定、承担行动与后果？他诊时同时记清记录者，记录者不自动成为 Owner。
2. **利害**：需要改变什么现实？做错或不做的主要代价是什么、会影响谁？
3. **可逆性**：撤回需要多少时间、成本和协调？能否先做小型可逆行动？

再辨认主要不清晰来自哪里：`desire / goal / problem / strategy / execution`。可以多项共存，但只说一个当前主攻点，并请 Owner 裁决：

> 我判断现在主要卡在 ___，依据是 ___。这个判断对吗？

正式化时三项都要被**记录**，但不要求都能确认：拿不到就写 `unknown` 并说明原因。若 Owner 不明 / 不在场，或利害、可逆性因 blocker 无法确认，进入 `cannot_proceed`；不得用「尚未确认」堵死这个合法出口。这些要求不追溯约束之前的 Work 对话。

## Step 1 · 正式化时五选一

| 路由 | 何时选 | 本轮要做什么 |
|---|---|---|
| `no_framework` | 代价低、可逆，试一次比继续分析便宜；或已知道该做什么，只是缺行动 | 不套框架，直接约定一个小型可逆动作 |
| `evidence_first` | 一个关键未知会改变选择，现有信息不足以判断 | 指定要取的证据、取得方法和返回时间 |
| `cannot_proceed` | Owner 不明 / 不在场、权限缺失、依赖未满足或其他 blocker 使本轮无法推进 | 记录 blocker、解除条件和重访时间 |
| `Quick` | 日常、代价有限、可逆，但仍需正式收束判断 | 复用 Work 内容，只补关键缺口，形成轻量出口 |
| `Full` | 重大、高代价、难逆、影响多人，或需严肃消化外部建议 | 追问到关键冲突被 Owner 裁决，形成完整 Case |

用户已同意正式化但深度不确定时先走 Quick；尚未同意时继续 Work。发现利害或不可逆性高于预期就建议升级 Full，经用户接受后再升级；若用户拒绝升级，必须回到 Work 或改走实际匹配的非答案出口，只能保留可逆的临时保护动作，不得以 Quick 正常决策收尾或认可不可逆承诺。正式化后若用户重新打开问题、想继续发散或前提发生变化，可以回到 Work；保留已经得到的信息，不把未完成的正式化伪装成决策快照。`no_framework`、`evidence_first`、`cannot_proceed` 是三个合法的非答案出口，不是失败，也不应为了显得完整而硬凑判断。

## Step 2 · 按 CATALOG 路由选框架

只在 Quick / Full 确实需要时选择。**[frameworks/CATALOG.md](../../../frameworks/CATALOG.md) 的「路由」是框架选择的唯一事实源。** 每次直接读取其当前版本，不在本 Skill 复制环节或候选表，也不凭记忆、视角或话题关键词选工具。

按 CATALOG 当前路由逐步做：

1. 先走入口筛选，作为 Step 1 分流的一致性检查；若发现实际应走非答案出口，就改最终处置，不为保住 Quick / Full 而硬套框架。
2. 对仍进入 Quick / Full 的情境，沿它定义的思考流水线从上游到下游逐环自检；**第一个没过的环就是断点**，不要越过上游问题去优化下游。
3. 在断点所在环按当前判据分叉选定框架。自诊与他诊使用同一套路由；商业框架没有优先权，只有该环当前判据匹配时才选。
4. 任何时刻最多使用两个思考工具，也可以一个都不用。若已有一套仍在使用的 `Specialist Method`，本步最多再选一个 `CATALOG` 框架；没有使用、或已经弃用专门方法时，才可从 `CATALOG` 选到两个。组合仅限跨环上下游或正反面；同环工具不要叠。
5. 对照每个框架的「什么时候别用」。命中不适用条件就换掉或不用；用大约十分钟仍没看见新东西，或开始给既有结论找证据，也立刻换掉，总使用量仍不得超过两个。
6. 写一句「它让我看见了什么之前没看见的」。写不出就把本次框架记为不适用。

CATALOG 当前框架都不匹配是正常结果。按它的兜底合同记录断点、情境与不匹配原因，不临时发明行业专用框架。

## Step 3 · 正式化时只补关键缺口

- 不重演 Work 对话。先列出「已知 / 仍缺 / 为什么缺口会改变结论」，只追问会影响路由、判断或行动合同的内容。
- 没有固定 3–5 轮要求，也不强制一次只问一个；优先用最少问题完成收束。选择题只在用户卡住时兜底，并保留「以上都不对」。
- 主动区分事实、证言、推断、估算和未知。外部建议、个人经验和类比标明出处与适用边界。
- 先采用用户已经表达的目标与判断，再给推荐判断作对照，避免把答案塞进问题里。
- 他诊或使用外部建议时，显式并列 `Owner Goal` 与建议者 / 记录者的默认目标；无冲突也要记录，存在冲突必须由 Owner 裁决。
- 前后说法冲突时指出并请 Owner 裁决；Copilot / 记录者不能替 Owner 接受目标、门槛或代价。
- Owner 若修改或拒绝推荐判断，记录 Owner 的最终替代判断；若尚无最终判断，就改走 `no_framework`、`evidence_first` 或 `cannot_proceed` 中实际匹配的一路。在此之前不能按正常决策出口收尾，也不能计入首批验证。
- Full 承诺前做 Teach-back：Owner 用自己的话说出问题、选择、权衡、门槛和改变判断的条件，并能明确不同意或修改。

## Step 4 · 正式出口合同

### 正常决策出口（Quick / Full）

进入出口前必须有 Owner 确认的成功边界。Full 使用完整 `Success Contract`；Quick 使用轻量版，但仍要写清：Owner 要改变的现实、可观察成功信号、可接受投入，以及不可接受代价 / 反目标 / 失败线。若是他诊或使用外部建议，还要显示建议者 / 记录者的默认目标、是否冲突及 Owner 裁决。缺任一适用项就继续澄清或改走非答案出口，不能假装已有决策。

三个字段缺一不可，口头收尾也一样：

- **动作**：下一件具体到能开始的事；Full 还要写负责人和承诺确认。
- **门槛**：可观察、有窗口，且能判断继续、停止或修订；来源不可靠的数字只能标作候选。
- **复盘日期**：何时拿现实结果回来对照判断。

### 三个非答案出口

- `no_framework`：写明为什么不需要框架、直接做的可逆动作、要观察什么，以及复盘日期。
- `evidence_first`：写明缺哪一项具体证据、由谁如何取得，以及回到判断的日期。证据回来前不硬下结论。
- `cannot_proceed`：写明 blocker、谁或什么条件能解除，以及重访日期。没有解除路径时也如实写明，不伪造动作。

它们按各自合同收尾就是完成，不能标记为失败。若不重进且不再安排日期，必须写明关闭理由；不能用一个无解释的「结束」代替去向。

## Step 5 · 记录与验证批次

**GPT Work 不直接落 ThinkingCase，也不计入验证。** 用户要保存 Work 中形成的判断、承诺或复盘时，先选择 Quick / Full，再把已有对话综合进对应模板。未计入验证批次的轻量自诊 Quick 可以只在对话中给出出口合同；但正常决策仍必须有动作、门槛、复盘日期，非答案出口仍按上节收尾。下列强制落盘情形优先于此默认值。

以下情况要写文件：

- 计入首批 5 次验证（目标构成为 3 次自诊 + 2 次他诊）的 session，**强制落 `cases/`**；必须记录「验证序号 __ / 5、视角、初始 / 最终处置、复盘日期」，才能计数。
- Full，以及所有**已正式化**的重大 / 高代价 / 难逆事项，不论最终处置或是否已经形成判断。
- 所有**已正式化**的他诊，不论档位、路由或是否计入验证；记录者与 Owner 必须分开。仍在 Work 中的他诊不因视角本身被迫落盘。
- 任何需要保留真实第三方谈话、姓名、数字或名单的记录；只允许写入 `cases/` 或 `_private/`。

首批 5 次的计数口径：

- 只有实际进入 Quick 或 Full，形成当前最佳判断，并以「动作 + 门槛 + 复盘日期」正常收尾的 session 才能计入。
- Owner 修改或拒绝推荐判断时，只有 Owner 的最终替代判断已记录且正常收尾，才能计入；仍无最终判断就不计数。
- `no_framework`、`evidence_first`、`cannot_proceed` 在不命中上述强制落盘条件时可以按需留一份 Quick 记录，但**不计入 5 次**；它们没有足够的判断快照，不能验证「当时为什么这么定、什么证据会改变判断」。
- 计数目标保持 3 次自诊 + 2 次他诊；视角以 Case Owner 与记录者字段为准，不能事后改标签凑数。

模板选择（仅正式化后）：

- Quick → `templates/case-quick.md`
- Full → `templates/case-full.md`
- 三个非答案出口若要留档 → 用 `case-quick.md` 简记，最终处置保持原值、验证批次写「不计入」，不能伪装成 Quick 判断。

若一份 Quick / Full 已经开始并落盘，后来因目标未确认、Owner 无最终判断或拒绝承诺而转为非答案出口，**保留同一份记录，不换模板、不删除已产生的推理**。初始处置保持原值，另记最终处置为 `no_framework`、`evidence_first` 或 `cannot_proceed`，只填对应出口合同；不得冻结虚假的正常决策快照，也不得计入首批验证。

若正式化尚未收束就回到 Work，已有文件只保留为未定草稿：最终处置保持 `未定`，不冻结决策快照、不填验证序号，也不声称完成 Case。以后再次正式化时复用它或按谱系新建后续 Case，不要求重讲背景。

写到 `cases/THK-{NNN}-{slug}.md`：编号取 `cases/` 下现有最大值 + 1，目录不存在就建。主入口始终是 `cases/THK-NNN`，不按视角另建模板或目录。

已落盘的非答案出口后来重新 Triage 时，不改原文件的最终处置。若进入新的 Quick / Full 判断，创建一份新 Case：旧文件写 `follow_up_case`，新文件写 `origin_case`，双向链接；只有新 Case 满足正常决策出口时才可计数。未落盘的非答案出口直接在原对话重新 Triage。

**隐私纪律（硬性）**：真实姓名、营收、客户名单、第三方谈话记录只允许出现在 `cases/` 和 `_private/`，两者均被 gitignore。绝不把真实素材写入 `templates/`、`frameworks/`、`docs/` 或本 Skill；产品文件中的说明必须使用中性表述。

每份落盘记录最后统一写三行：

```text
- 哪一步卡住：
- 哪个问题白问：
- 哪个步骤或检查多余：
```
