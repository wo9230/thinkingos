# ThinkingOS V0.1 建造契约（MVP）

**文档类型**：v0.1 施工清单
**状态**：已接受，取代 PRD-v0.2 作为 v0.1 的建造依据
**日期**：2026-08-13
**与 PRD 的关系**：[PRD-v0.2.md](PRD-v0.2.md) 是长期产品契约（North Star），**不是施工图**。二者冲突时，v0.1 以本文件为准。

---

## 1. 为什么需要这份文件

PRD-v0.2 定义的长期产品用 8 道 fail-closed Gate 与 Teach-back，把重大情境审计成可追溯判断。这个方向保留，但其完整运行时尚不是 v0.1 要验证的最小形态。

v0.1 的方向是日常反复使用，并同时支持「自诊」与「他诊」两种视角。若每次使用都必须经过完整状态机，流程负担会先于产品价值出现。现阶段的首要不确定性不是规则是否足够完备，而是这套工具能否被实际使用并带来可复盘的下一步。

## 2. 核心裁决：默认 GPT Work，正式收束只有两档

`GPT Work` 是默认自由协作态：可以直接回答、探索、推演、反驳、脑暴或自然结束，不要求先完成 Triage、命名 Case Owner、选择路由、填写 Success Contract 或产出行动合同。它不是第三档、Case 类型、状态或验证样本，也不创建 `case-work`。

当用户明确要收束判断、冻结承诺、落盘、计入验证，或重大 / 高代价 / 难逆事项准备确认不可逆行动时，才从已有对话转入下面两种正式深度。转换只补真正缺失的信息，不从头重跑问卷。正式化之前仍可给临时判断与可逆的安全缓冲；用户可以拒绝正式化并继续探索，但此时不得认可不可逆承诺或把分析称为已经完成的重大决策。

| | 快档 Quick Pass | 重档 Full Case |
|---|---|---|
| 触发 | 用户要正式收束，且事项日常、代价有限、可逆 | 用户接受正式化，且事项重大 / 难逆 / 代价高 / 需严肃消化外部建议 |
| 时长 | 通常较短，不设硬时限 | 视重大问题所需，不设硬时限 |
| 追问轮次 | 复用 Work 内容，只补关键缺口 | 只追问影响判断、承诺或复盘的缺口 |
| 产物 | 轻量自诊可仅保留对话内一页式总结；需落盘时使用 `case-quick` | 对话内完整总结，并使用 `case-full` 落盘 |
| Gate | 无正式 Gate。轻量出口检查：Owner 已确认成功边界，并有动作、门槛与复盘日期 | PRD 的 8 个 Gate **降级成勾选式检查清单** |
| Schema 校验 | 无 | 无（v0.1 不上 YAML） |

**Gate 降级的含义**：`G-01`…`G-08` 的**内容**全部保留，作为重档收尾时的自检清单；但它们不再是阻塞状态迁移的 fail-closed 机制。理由：fail-closed Gate 需要一个执行它的运行时，v0.1 没有运行时，只有一个人和一个 skill。把它写成检查清单，人会看；写成状态机，人会绕过。

**档位与视角是两件事**：Quick / Full 是处理深度，决定本次投入多少；自诊 / 他诊只是问题归属视角，不构成第三档，也不改变两档的出口。

**落盘与计数规则**：Work 不直接落 ThinkingCase，也不计数。进入正式化后，Full、重大 / 高代价 / 难逆、他诊，以及计入首批 5 次验证的 session 必须创建 Case 文件。计入验证的 session 还必须进入 Quick 或 Full、形成正常决策出口，分别写入 `case-quick` 或 `case-full`，并记录复盘日期。`不需要跑流程`、`证据不足`、`当前卡住` 三种非答案出口可以记录，但不计入首批 5 次。

## 3. 快档规格

```
从 GPT Work 已有对话综合 Triage
  → 只补会改变判断或出口的缺口
  → Owner 确认轻量成功契约
  → 一页式总结（验证 session 必须落盘为 case）
  → 一个下一步动作 + 一个可观察门槛 + 一个复盘日期
```

**轻量成功契约**：Quick 正常决策仍受 `C-01` 约束，但只需确认 Owner 要改变的现实、一个可观察成功信号、可接受投入，以及不可接受代价 / 反目标 / 失败线；不要求复制 Full 的完整表格。非答案出口不伪造成功契约。正式化前的 Work 不受这张表单约束，但不得悄悄替换用户目标。

未落盘的 Quick 以原对话或一页式总结作为复盘快照；到期后必须回到该记录追加结果。原记录无法找回时，不得声称完成了复盘或从中形成判断更新。

**必须支持的非答案出口**（承接 PRD `FR-031`，这条很关键）：

- `不需要跑流程` —— 低风险可逆的事，直接去做。这是**合法且常见**的输出，不是失败。
- `证据不足` —— 先去取一个具体信息，再回来。
- `当前卡住` —— 有 blocker，本次无法推进，记下 blocker 就结束。

没有这三个出口，工具会退化成「必须走完的仪式」，然后被弃用。

## 4. 重档规格

沿用 PRD 的流程骨架，但产物是 `case-full` 一份 Markdown，不是 17 段 YAML。

收尾时对照 8 项检查清单（详见 [templates/case-full.md](../../templates/case-full.md) 尾部）。任何一项未过，**记录未过 + 原因**即可，不阻塞。

Quick / Full 进行中若回到 Work，保留已得到的信息并停止正式收束；已落盘文件只作为最终处置未定的草稿，不伪造决策快照或完成状态。若改走 `不需要跑流程`、`证据不足` 或 `当前卡住`，保留同一份已落盘记录，另记最终处置并填写对应非答案出口；不伪造正常决策快照，也不计入首批验证。

## 5. v0.1 明确不做

**冻结（文件已存在，v0.1 不引用、不扩充）**：

- `schemas/thinking-case.schema.yaml` —— 17 段 JSON Schema，v0.2 资产

> 这是已经存在的 v0.2 资产。v0.1 的 skill 和模板一律不读它；先跑够 5 次，再决定是否启用或调整。

**不建**：

- Case 状态机 / 状态迁移引擎
- `domain-packs/` 与任何候选规则包
- `evals/` 与任何自动或固定评测协议
- 多 Agent、Advisor 模拟、导师团
- 任何 UI / Web / dashboard
- 复制上游 `thinking-framework-skills` 的 63 个 framework
- 重写追问引擎；v0.1 的追问纪律由 `clarify` Skill 自身承担，不依赖未分发的全局 Skill

这项范围纪律不禁止按需读取已有的外部或私有知识源。按 `D-026`，领域课程和操作方法只能作为有来源、有适用边界的专门方法被渐进检索；它们不复制进 `CATALOG`，不变成 `domain-pack`，也不要求普通问答先跑一遍方法流程。

## 7. 验收

不看功能数量、文档长度、Gate 数量。只看一条：

> 拿一个**真实正在纠结**的决策跑一遍。到记录的复盘日期回看那份 Case，能不能说出「我当时为什么这么定、什么证据会让我改主意」。

- 说不出来 → 模板有问题，改模板
- 说得出来但没再打开过 → 入口有问题（太重 / 想不起来用）
- 5 次跑完还想跑第 6 次 → 这时候才重访 schema、domain packs、evals 是否值得建设

同时观察但**不计入 5 个 Case**：Work 是否让用户愿意继续对话、正式化建议被接受或拒绝的原因、转入 Quick / Full 时是否重复盘问，以及哪些问题在 Work 中已自然解决。这些只用于判断入口摩擦，不把普通问答伪装成验证 Case。

**跑满 5 次（3 次自诊 + 2 次他诊）之前，不许建第 5 节列出的任何东西。**GPT Work 不计数；自诊 / 他诊只作为正式 Case 的视角记录，不形成第三档；`3 + 2` 是首批验证样本构成，不是产品档位。计入这 5 次的每个 session 都必须进入 Quick 或 Full、形成正常决策出口、落盘为对应 Case，并写明复盘日期；非答案出口不计数。

每次统一记录三行：哪一步卡住 / 哪个问题白问 / 哪个步骤或检查多余。
