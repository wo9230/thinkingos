## 0. 提案摘要

本提案建议将 ThinkingOS 从单次情境的判断副驾，扩展为持续连接人生方向、阶段目标、项目、日常行动与现实反馈的个人导航与执行系统。

若该方向经证据验证并正式生效，产品继续保留现有的判断能力：自由协作、问题澄清、通用框架、证据纪律、Quick / Full、行动与复盘。它们在新结构中承担“思考与判断引擎”，不再单独代表整个产品。

V0.3 的最小可信路径不是一次性建设完整平台，而是让一位 `Owner` 反复跑通以下导航循环：

```text
恢复方向与现实状态
  → 识别当前阶段
  → 确定当前主线与探索池
  → 形成本周可观察结果
  → 安排今日关键行动与必要维护
  → 记录现实反馈
  → 复盘并更新下一轮导航
```

只有真实使用反复证明某个环节需要持久化、集成、自动化或 Agent，才扩建对应能力。

本提案自身也受同一纪律约束：它在 v0.1 验证（首批 5 个正式 Case）完成之前提出，因此只提供方向候选，不构成「单次判断价值单元不足」的证据。这一结论必须由真实使用数据支持或推翻，路径见 §13 Phase D。

## 1. 产品问题

### 1.1 用户面对的现实

一个人往往同时承担多种责任：长期生活建设、健康维护、学习、工作、项目、商业经营和机会探索。这些内容来自不同时间尺度，却共同竞争同一份时间、精力、注意力和资金。

常见问题包括：

- 长期方向存在，但没有稳定连接到阶段目标和今日行动。
- 工作、项目、学习和商业事项被分别管理，看不见它们之间的因果关系。
- 新兴趣和新机会不断进入，当前主线频繁被打断。
- 大量时间用于研究工具、搭建系统和整理资料，现实输出与外部反馈不足。
- 普通任务清单只能记录“做什么”，不能判断“为什么现在做、做完改变什么”。
- 通用问答能给建议，但缺少连续状态，用户需要反复解释背景。
- 专业方法很多，缺少按当前问题选择、验证和退出的方法。
- 健康、精力和不可牺牲的生活边界没有进入计划约束。
- 完成产物、完成执行、获得外部反馈和获得业务结果经常被混为同一种“完成”。

### 1.2 当前产品缺口

现有 ThinkingOS 能把模糊情境变成较清晰的判断、行动和复盘，但缺少：

- 跨时间尺度的持续目标地图。
- 人生方向、阶段主线、项目和日常行动之间的连接。
- 多项目之间的容量、依赖、优先级和暂停机制。
- 健康、精力、承诺与探索需求的共同约束。
- 面向商业、项目、学习和生活问题的专门方法调用。
- 年、月、周、日可连续恢复的执行工作台。
- 从现实数据更新目标、项目和判断的导航循环。

### 1.3 需要改变的现实

在任意工作时点，`Owner` 能用很低的恢复成本回答：

1. 我正在建设什么长期方向？
2. 我现在处于哪个阶段？
3. 当前最重要的一项结果是什么？
4. 今天应推进哪一步，哪些事暂时不做？
5. 这一步与长期方向、项目和现实反馈有什么关系？
6. 什么结果会让我继续、停止或调整？

## 2. 产品定义

### 2.1 产品命题

ThinkingOS 是一个个人导航与执行系统。它将混乱输入和现实状态连接到长期方向、阶段目标、当前主线、项目与日常行动，并通过通用判断框架、专门方法和现实反馈持续修订路线。

### 2.2 产品承诺

ThinkingOS 帮助 `Owner`：

- 看清当前所处位置和主要约束。
- 维护长期方向与不可牺牲边界。
- 在多个目标中选出阶段主线。
- 将目标拆成项目、习惯、下一步和反馈信号。
- 将新兴趣和新机会放入可控探索池。
- 在需要时调用有来源、有边界的专业方法。
- 将计划落入年、月、周、日工作节奏。
- 根据实际执行、健康状态和外部结果更新路线。

### 2.3 产品不承诺

- 不保证人生、项目或商业必然成功。
- 不替 `Owner` 选择价值观、人生目标或不可逆承诺。
- 不把所有生活活动量化为 KPI。
- 不要求每次交流走完一套固定流程。
- 不把作者经验、课程案例或模型输出自动升级为普遍规律。
- 不通过功能数量、Agent 数量或文档规模证明产品价值。
- 不以全天监控、完整个人画像或无限数据收集为前提。
- 不把工作台扩建本身当作目标进展。

### 2.4 North Star

`Owner` 在现实发生变化时，仍能快速恢复方向、看见当前主线、采取一个与目标一致的行动，并在得到反馈后调整下一轮导航。

## 3. 设计原则

### P-01 · 一张地图，多种尺度

人生方向、阶段目标、项目、周结果和今日行动必须可追溯连接，不建立互不相干的目标系统。

### P-02 · 当前主线保持单一

同一容量范围内默认只保护一条当前主线。其他重要事项可以作为维护责任、并行依赖或探索项存在，但不能都被标成最高优先级。

### P-03 · 探索是受保护的合法需求

新兴趣和新机会进入探索池。探索获得空间，但不自动打断当前主线；只有证据表明其价值、时机或风险发生变化时才升级。

### P-04 · 健康和底线先作为约束

健康、家庭、法律、财务安全、既有承诺及其他不可牺牲边界进入计划约束，不能等排完工作后再补。

### P-05 · 先识别阶段和瓶颈

计划从当前现实、阶段和瓶颈开始。系统不得因为长期方向重要，就同时展开所有下游项目。

### P-06 · 学习服务于能力与行动

学习分为解除当前卡点的定向学习、长期能力积累和探索性学习。三者可以共存，但必须知道各自在服务什么。

### P-07 · 外部结果高于内部完成感

文件、提示词、系统、内容草稿和技术验证属于不同完成层。需要外部反馈或业务验证的事项，不能以内部产物完成代替现实结果。

### P-08 · 规则做护栏，模型保留判断

隐私、目标主权、证据纪律、不可逆边界和健康底线属于硬约束。问题分解、方法选择、追问深度和计划表达根据上下文灵活处理。

### P-09 · 自动化排在删除与简化之后

先质疑任务是否需要存在，再删除、简化和跑通，最后才建立 SOP、自动化或 Agent。

### P-10 · 所有学习都由现实反馈赚得

系统保留当时的目标、判断、行动和预测，再与实际结果对照。不得在结果已知后改写原判断。

## 4. 产品分层

### 4.1 Owner 现实模型

维护会改变导航结果的最小上下文：

- 长期方向与期望生活。
- 价值选择与不可牺牲边界。
- 当前角色、责任和既有承诺。
- 可用时间、精力、资金、能力和关系资源。
- 健康与恢复约束。
- 已确认事实、暂时判断和未知。

只保存会影响当前判断或连续性的内容，不追求完整人格画像。

### 4.2 目标导航层

连接以下层级：

```text
Life Compass
  → Long-term Direction
  → Stage Goal
  → Current Mainline
  → Project / Habit
  → Weekly Outcome
  → Daily Action
```

每一层必须说明它服务哪一层、什么结果算推进、何时重访。

### 4.3 思考与判断引擎

复用现有资产：

- GPT Work 自由协作入口。
- `frameworks/CATALOG.md` 的通用判断框架。
- `clarify` 的澄清、证据、判断与正式化能力。
- Quick / Full 的可反证判断、行动和复盘记录。

ThinkingCase 继续处理局部复杂判断；它成为导航系统中的一种工作对象，不再独自承担全部产品价值。

### 4.4 专门方法层

当通用模型能力不足以支撑具体对象时，按当前问题调用有来源的方法，例如：

- 客户与市场。
- 产品与价值主张。
- 内容、传播与个人品牌。
- 增长、销售与转化。
- 交付、运营与项目管理。
- 学习、教学与能力建设。
- 健康、精力和习惯。

专门方法必须记录来源、适用条件、必要输入、禁用条件和证伪方式。一次只调用解决当前断点所需的最小方法，不建立方法迷宫。

### 4.5 执行工作台

提供可连续恢复的：

- 年度方向页。
- 月度重点页。
- 周导航页。
- 每日工作页。
- 项目页。
- 探索池。
- 等待与承诺清单。
- 复盘记录。

工作台显示关系和状态，不复制同一事项到多个互不一致的清单。

### 4.6 反馈与学习层

区分并连接：

- 行动是否发生。
- 产物是否完成。
- 技术或质量是否验证。
- 外部对象是否看到、使用或回应。
- 业务或生活结果是否发生。
- 结果来自判断、执行、环境还是运气。

### 4.7 SOP、自动化与 Agent 层

只有满足以下条件的工作才进入自动化候选：

- 任务被证明有必要存在。
- 流程已经由人完整跑通。
- 输入、输出和质量判断相对稳定。
- 重复成本确实影响当前瓶颈。
- 自动化的维护成本低于节省的成本。

Agent 不拥有 `Owner Goal`，不自主接受不可逆承诺，也不在来源不足时伪造事实。

## 5. 核心对象（候选概念模型）

| 对象 | 用途 | 最小字段 |
|---|---|---|
| `LifeCompass` | 记录长期生活方向和边界 | desired life、value、boundary、review cadence |
| `Direction` | 表达长期建设方向 | outcome、reason、time horizon、status |
| `StageGoal` | 当前阶段需要改变的现实 | current state、target state、success signal、review condition |
| `Mainline` | 当前受保护的一项关键结果 | linked goal、bottleneck、current outcome、stop condition |
| `MaintenanceArea` | 必须维持但不属于主线的责任 | minimum standard、cadence、risk signal |
| `Project` | 产生明确结果的有限工作 | outcome、milestone、next action、dependency、status |
| `Habit` | 通过重复支持能力或健康 | purpose、cue、minimum version、feedback |
| `ExplorationItem` | 暂不打断主线的新兴趣或机会 | hypothesis、small probe、promotion condition、expiry/review |
| `Commitment` | 对他人或未来时间的约束 | owner、counterparty、due condition、reversibility |
| `WeeklyOutcome` | 本周要观察到的现实变化 | linked mainline、signal、window、result |
| `DailyAction` | 当天能开始的关键动作 | linked outcome、start condition、done evidence |
| `ThinkingCase` | 处理复杂或重大判断 | 复用现有定义 |
| `SpecialistMethod` | 提供领域特有的方法 | source、problem shape、inputs、steps、limits |
| `Outcome` | 记录现实结果 | source、date、evidence type、interpretation |
| `AgentCandidate` | 等待验证的自动化机会 | repeated workflow、cost、stability、risk、promotion condition |

这些是产品概念，不构成 v0.1 schema 变更。只有实际使用证明某对象需要独立持久化时才进入实现契约。

## 6. 核心用户流程

### WF-01 · 混乱输入收集

`Owner` 可以直接输入想法、任务、担忧、机会、学习内容或现实变化。系统应：

1. 恢复已有方向和当前状态。
2. 判断新输入属于方向、目标、项目、行动、维护、探索、证据或未解问题。
3. 发现与既有内容的重复、矛盾和依赖。
4. 只追问会改变归属、优先级或行动的缺口。
5. 更新当前地图或给出临时建议。

### WF-02 · 方向与阶段导航

系统帮助 `Owner`：

1. 描述想改变的长期现实和不可牺牲边界。
2. 识别当前阶段及其主要限制。
3. 选择当前阶段的一项关键结果。
4. 明确维护责任和探索空间。
5. 记录什么证据会触发换阶段或换主线。

### WF-03 · 目标拆解

系统将阶段目标拆成：

- 有明确结果的项目。
- 支持能力或健康的习惯。
- 当前下一步。
- 可观察反馈信号。
- 依赖、等待和停止条件。

拆解必须停在能够执行和验证的层级，不为完整而生成大量占位任务。

### WF-04 · 专业问题处理

当问题涉及具体领域：

1. 先确定当前断点和必要输入。
2. 检索一套最匹配的专门方法。
3. 区分来源主张、案例、方法步骤、当前事实和推断。
4. 将方法应用到本案，形成候选判断或路径。
5. 用现实动作验证，不把方法权威当作结论。

### WF-05 · 周导航

每周恢复：

- 当前阶段目标。
- 当前主线与瓶颈。
- 上周结果和新证据。
- 本周一项关键结果。
- 必须维护的责任。
- 可以进行的探索。
- 暂停或删除的事项。
- 本周复盘条件。

### WF-06 · 日导航

每日工作页优先显示：

- 本周关键结果。
- 今天最重要的一项行动。
- 已承诺且临近的交付。
- 健康与恢复的最低边界。
- 集中处理的维护事项。
- 今天不做的内容。
- 有余量时才进入的探索。

### WF-07 · 新任务与机会裁决

新事项进入时，系统依据：

- 与阶段目标和当前主线的关系。
- 时间、精力和资金容量。
- 机会成本与可逆性。
- 已有承诺与健康边界。
- 能否提供高信息增益的小型验证。

给出以下一种处理：立即行动、排入当前窗口、批量处理、委托、进入探索池、等待条件、暂停或删除。

### WF-08 · 复盘与路线更新

复盘依次检查：

1. 原计划和承诺是什么。
2. 实际行动和结果是什么。
3. 哪些结果来自判断、执行、环境或运气。
4. 当前阶段、瓶颈或主线是否变化。
5. 哪些项目继续、停止、调整或升级。
6. 哪项重复工作可以进入 SOP 或 Agent 候选。

## 7. 功能需求

### 7.1 P0 · 最小导航循环

| ID | 需求 |
|---|---|
| NAV-FR-001 | 系统必须能从既有记录恢复长期方向、阶段目标和当前主线，缺失时明确显示未知。 |
| NAV-FR-002 | 系统必须能把新输入放入目标、项目、行动、维护、探索、证据或未解问题中的合适位置。 |
| NAV-FR-003 | 系统必须生成一份可追溯到阶段目标的周导航页。 |
| NAV-FR-004 | 系统必须生成一份可追溯到周结果的每日工作页。 |
| NAV-FR-005 | 每日工作页必须同时显示关键行动、必要维护、健康边界和“不做清单”。 |
| NAV-FR-006 | 系统必须限制当前主线，并把其他新机会放入探索池或等待状态。 |
| NAV-FR-007 | 当输入暴露复杂判断时，系统必须复用现有 GPT Work / Quick / Full，而不是复制一套判断流程。 |
| NAV-FR-008 | 系统必须记录周结果的现实证据，并据此更新下一周导航。 |
| NAV-FR-009 | 系统必须区分产物完成、执行完成、外部反馈和结果验证。 |
| NAV-FR-010 | 系统不得在没有来源或实际数据时伪造成功门槛、商业结论或健康建议。 |

### 7.2 P1 · 目标、项目与专业方法

| ID | 需求 |
|---|---|
| NAV-FR-101 | 支持年度方向、月度重点、项目和习惯与周导航的连接。 |
| NAV-FR-102 | 支持项目依赖、等待、暂停、停止和下一步。 |
| NAV-FR-103 | 支持按问题对象与断点调用 `SpecialistMethod`。 |

| NAV-FR-106 | 支持从项目和复盘中识别可复用 SOP。 |

|---|---|
| NAV-FR-201 | 在获得授权的来源范围内，检测截止时间、长期停滞、WIP 过载和健康边界风险。 |
| NAV-FR-202 | 根据新证据提出优先级调整，但未经 `Owner` 确认不改写长期目标。 |
| NAV-FR-203 | 为稳定重复流程创建 `AgentCandidate`，通过验证后再实现 Agent。 |
| NAV-FR-204 | Agent 产出必须回到项目、行动或证据对象，不形成独立信息孤岛。 |
| NAV-FR-205 | 支持授权范围内的日程、任务、内容、客户和结果数据连接。 |

## 8. 非功能需求

| ID | 要求 |
|---|---|
| NAV-NFR-001 | **低恢复成本**：用户不应在每次会话重新解释已持久化的目标、项目和已确认事实。 |
| NAV-NFR-002 | **低仪式感**：简单事项可直接处理；正式结构只在能减少混乱或支持复盘时出现。 |
| NAV-NFR-003 | **可追溯性**：每日行动可以追溯到周结果、项目和阶段目标。 |
| NAV-NFR-004 | **状态诚实**：未知、推断、未验证、等待和已完成必须可区分。 |
| NAV-NFR-005 | **隐私最小化**：产品文件保持领域中立；真实个人、健康、业务和第三方信息只进入授权的私有存储。 |
| NAV-NFR-006 | **可修订性**：目标、计划和方法可以因新证据更新，但历史判断和结果记录不得被覆盖。 |
| NAV-NFR-007 | **维护成本可见**：任何新页面、字段、集成、自动化和 Agent 都必须说明持续维护者和退出路径。 |
| NAV-NFR-008 | **来源边界**：外部课程、书籍、案例和建议保留来源、适用条件与不确定性。 |
| NAV-NFR-009 | **用户主权**：系统可以挑战、推荐和提醒，最终目标、代价和不可逆承诺由 `Owner` 决定。 |

## 9. P0 信息架构与产物

P0 只需要以下最小产物：

```text
navigation/
  compass.md          # 长期方向、边界与当前阶段
  map.md              # 目标、主线、项目、维护与探索的关系
  weekly.md           # 当前周导航与结果
  daily/YYYY-MM-DD.md # 当日行动、维护、健康边界与结果
  reviews/            # 周期复盘
```

此目录只是候选表达。正式采用前必须确认它与现有工作台的单一事实源关系，避免复制两套目标和任务。

P0 不需要：

- 新 UI 或 dashboard。
- 新状态机或 YAML schema。
- 多 Agent 编排。
- 自动抓取全部个人数据。
- 完整商业、健康或人生方法库。
- 把所有历史聊天一次性结构化。

## 10. 验收标准

### 10.1 最小导航循环验收

完成一个真实周循环后，可以回答：

- 长期方向、阶段目标和本周结果之间是否存在清晰连接？
- 每天是否能快速确定一项关键行动？
- 新事项是否被正确处理，而没有自动打断主线？
- 健康和既有承诺是否在计划前成为约束？
- 周末是否有现实证据判断继续、停止或调整？
- 用户是否减少了重新解释背景和重复整理项目状态？
- 系统是否删除了工作，还是增加了维护工作？

### 10.2 P0 通过条件

P0 只有在以下事实同时出现时才算有效：

1. `Owner` 实际使用了周导航和每日工作页。
2. 至少一项关键行动产生了可观察的现实结果或有效反馈。
3. 至少一个新事项被放入探索、等待、暂停或删除，而没有扩大当前 WIP。
4. 到期复盘真实发生，并基于证据更新了下一轮导航。
5. 现有 `clarify` 能在需要判断时被复用，没有产生第二套竞争流程。

具体数值门槛在获得真实基线后由 `Owner` 采纳，本提案不预设通用数字。

## 11. 风险与缓解

| 风险 | 表现 | 缓解 |
|---|---|---|
| 产品范围再次膨胀 | 同时建设目标管理、知识库、健康、CRM、内容和 Agent | P0 只跑导航周循环，其他层保持候选 |
| 系统建设替代执行 | 花时间改页面和字段，没有现实输出 | 每周验收必须包含外部结果或有效反馈 |
| 与现有工作台重复 | 同一任务在多个位置维护 | 实施前确定单一事实源，只做链接或视图 |
| 模型虚构个人状态 | 将推断写成已确认事实 | 状态标记来源和置信度，关键改变由 Owner 裁决 |
| 过度规则化 | 每次对话都要填表和走流程 | 保留 GPT Work，简单问题直接处理 |
| 目标过度单一 | 主线压制健康、责任和探索 | 主线、维护区和探索池同时存在，容量分别可见 |
| 专门方法迷宫 | 每个问题调用大量课程和框架 | 一次只修首个断点，默认一套专门方法 |
| 伪造成功确定性 | 把计划写得完整就声称能实现目标 | 明确成功概率、关键未知和现实验证 |
| Agent 维护反噬 | Agent 数量增长，输入输出不稳定 | 只自动化已跑通且影响瓶颈的流程 |
| 隐私泄露 | 真实个人和业务信息进入公开产品文件 | 产品文件领域中立，真实信息进入受控私有存储 |

## 13. 迭代顺序

### Phase A · 产品负责人审阅

- 审阅候选产品定义、North Star 假设、反目标和 P0 导航循环。
- 标出不同意、需要修改和仍未知的部分。
- 决定是否接受为下一轮 `Provisional` 方向候选；此处不作正式产品边界变更。

### Phase B · 决策与词汇对齐

- 新增一条 `Provisional` Decision Log，记录方向候选、证据门槛和放弃条件，不取代既有裁决。
- 候选概念留在本提案内；产品边界正式改变前，不改写 `CONTEXT.md` 的正式定义。
- 明确 `MVP-v0.1.md` 继续作为当前施工和验证契约。

### Phase C · 无建设验证准备

- **阻塞决策**：先裁决目标、项目和每日行动的权威事实源，以及本轮验证只读哪些已有信息、把结果写回哪里。未裁决时 Phase C 不得开始。
- 只使用现有 GPT Work、Quick / Full 和既有事实源手工运行导航循环，不新建 `navigation/`、模板、状态机、UI、Agent 或其他产品结构。
- 定义本轮需要观察的导航结果和 Case 计数口径，不修改现行规则。

### Phase D · 真实周循环（共享证据，分别验收）

- 使用真实方向、项目和工作负荷运行一个完整周循环。
- 周循环与 v0.1 验证可以共享真实情境和原始证据，但形成两个验收判断：周循环验证导航价值，正式 Case 验证现有判断引擎。
- 周内自然出现且满足 `MVP-v0.1.md` 全部条件的正式事项，才逐案进入 Quick / Full、落盘并计数；周循环本身不计作 ThinkingCase。
- 首批 5 Case 仍须满足 3 次自诊、2 次他诊及各自的正常决策出口和复盘日期。一周内不足 5 个时继续验证，不补造、不强制正式化，也不提前宣告验证债完成。
- 记录恢复成本、无效问题、WIP 变化、现实输出与复盘结果。
- 只修复真实出现的摩擦。

### Phase E · P0 设计与施工授权

- **前置条件（全部满足才进入）**：方向候选已由 `Provisional` Decision Log 记录；首批 5 Case 已达到 `MVP-v0.1.md` 的计数口径；至少一次 Phase D 周循环提供了可检查证据；单一事实源已经裁决；产品负责人已另行授权 P0。
- 任一条件未满足时不进入 P0。若要设置例外，必须由新 Decision Log 明确受影响的规则、证据、`Owner`、复查条件和回滚路径，不能以“验证合并”代替。
- 只设计 compass、map、weekly、daily、review 的最小表达。
- 定义 `clarify` 在导航循环中的调用边界。

### Phase F · 按证据扩展

- 重复出现的专业问题，接入一套专门方法。
- 重复出现的手工流程，整理 SOP。
- 稳定且影响瓶颈的 SOP，升级为 Agent 候选。
- UI、自动连接和多 Agent 必须分别通过维护成本与现实收益审查。

## 14. 阻塞决策与开放问题

这些问题不阻塞方向候选的审阅，但会影响验证或 P0 实施。

### 14.1 Phase C 阻塞决策

1. 现有生产工作台中，哪一处是目标、项目和每日行动的权威事实源？谁拥有写入权，其他位置如何只读、链接或处理冲突？

### 14.2 仍待回答

1. 导航状态需要自动从哪些已授权来源恢复，哪些必须由 `Owner` 明确输入？
2. 健康与精力只记录最低边界，还是需要连接更具体的数据？
3. 系统应在什么情况下主动提醒偏航，什么情况下保持安静？
4. 年、月、周、日中哪些层级需要独立页面，哪些只需要动态视图？
5. 专门方法的私有索引如何与公开、领域中立的产品文件隔离？

### 14.3 已裁决的记录关系

P0 周循环与 ThinkingCase 可以复用同一真实情境和原始证据，但分别形成验收结论。只有自然出现且满足 v0.1 全部计数条件的正式事项才生成并计入 Case；不为周循环重复录入，也不把周循环等同于一个或五个 Case。
